# Revisão técnica — Elite Dev 2026

## Objetivo e método

Esta revisão compara o enunciado `Desafio-Elite-Dev-2026.md` com a implementação real da branch base, sem tratar o README como prova suficiente. A análise percorreu a estrutura de pastas, o schema Prisma, as migrations SQL, os módulos NestJS, as páginas e hooks do Next.js, os testes existentes, os scripts de build/lint e as configurações de deploy. Depois da implementação desta branch, os mesmos comandos são executados novamente para separar claramente o estado inicial do estado entregue.

A arquitetura original foi preservada: `backend/` e `frontend/` continuam como aplicações irmãs; o backend segue organizado por feature com NestJS, Prisma, PostgreSQL, guards e decorators; o frontend mantém Next.js App Router, Tailwind/shadcn, TanStack Query, Zustand, React Hook Form/Zod e `motion`; as regras de negócio continuam no servidor; e o frontend não recebe segredos de APIs externas. Não foi criada uma integração MCP fictícia: no repositório, MCP aparece como referência de processo para pesquisa de componentes, não como contrato de runtime exigido pelo desafio.

## Achados priorizados

### P0 — e2e dependente de ambiente implícito

O teste e2e importava `AppModule`, que executa a validação completa das variáveis de ambiente, antes de qualquer fixture ser carregada. Em um checkout limpo sem `.env`, a aplicação de teste não inicializava, embora o teste substituísse o Prisma por um mock e não precisasse de PostgreSQL. Isso gerava quatro falhas de teste e ainda mascarava a cobertura real de health check, autenticação e `ValidationPipe`.

A correção adiciona `backend/test/jest-e2e.setup.ts`, carregado pelo próprio `jest-e2e.json`, com valores exclusivos de teste. O setup não desabilita validação, não cria banco e não reutiliza segredos de produção; apenas torna explícita a configuração mínima que o módulo já exigia. O comportamento de produção permanece inalterado.

### P0 — type-check do frontend não era independente do build

As páginas dinâmicas usavam o helper global `PageProps` gerado pelo Next.js. Depois de `next build`, o `.next/types` fazia o comando passar; em um checkout limpo, `tsc --noEmit` falhava porque os tipos gerados ainda não existiam. Isso enfraquecia o valor de qualquer gate de tipo executado antes do build.

A correção cria `frontend/src/types/next-page.ts` com o contrato explícito de Next.js 16 (`params: Promise<...>`) e aplica o tipo às páginas de organizador, checkout, detalhe de evento e compartilhamento. Durante a validação em clone novo, o mesmo princípio revelou uma dependência equivalente no `LayoutProps` global do layout raiz; ela também foi substituída pelo contrato estável `ReactNode`. O comportamento de runtime não muda. Também foi criado o script `npm run typecheck`, tornando o comando reproduzível e fácil de localizar.

### P1 — ausência de quality gate versionado

Não havia workflow em `.github/workflows`, portanto regressões de lint, tipos, testes, build ou dependências só seriam encontradas manualmente. A branch adiciona um workflow com jobs independentes para backend e frontend, cache de npm, Node.js 22, `npm ci`, lint não-mutante, type-check, testes unitários, e2e, build e auditoria de dependências no backend.

O lint original do backend continua disponível para uso local e autofix. Para CI, foi adicionado `lint:check`, que não altera o checkout. A auditoria usa o nível `high` para falhar diante de vulnerabilidades relevantes, sem transformar avisos de severidade inferior em falsos bloqueios.

### P1 — vulnerabilidade transitiva detectada pelo próprio lockfile

A auditoria inicial apontou `deepmerge-ts` 7.1.5, dependência transitiva de `@prisma/config`, com correção disponível na série 8.x. Em vez de fazer downgrade forçado do Prisma, foi aplicado um override explícito para `deepmerge-ts` 8.0.0. A árvore instalada foi conferida com `npm ls`, o Prisma Client continuou na versão original e o Swagger/compilação permanecem sob verificação pelos testes e build.

O override existente de `js-yaml` dentro do Swagger foi preservado. A decisão é deliberadamente pequena: corrige a dependência vulnerável sem trocar framework, banco, ORM ou contrato de API.

## Decisões que não foram alteradas

O mapa de assentos continua sendo responsabilidade da plataforma, pois o catálogo externo fornece metadados do evento, não o inventário de assentos do nosso venue. A garantia de concorrência continua em duas camadas: lock pessimista para serialização e índice único parcial como defesa no banco. O QR continua assinado com secret separado do JWT de autenticação e a portaria continua usando update condicional atômico para impedir dupla validação.

Também não foi introduzido WebSocket, refresh token, cadastro público ou multi-assento. Esses itens não são necessários para o fluxo avaliado e ampliariam a superfície da mudança sem resolver um defeito observado. O polling de 5 segundos, o JWT de demonstração de 24 horas e o escopo de uma reserva para um assento permanecem cortes documentados e coerentes com o prazo do desafio.

## Resultado da validação

A validação foi executada depois das mudanças, com instalação via `npm ci` em um clone novo da branch. O backend passou com 237 testes unitários e 4 testes e2e; o frontend passou com 53 testes de lógica/componente. O type-check foi executado antes do build e no clone sem `.next`, portanto não dependeu de tipos gerados anteriormente. A troca da imagem de eventos para `next/image` também eliminou o único warning de lint que havia restado no frontend.

A validação final desta branch comprova os itens abaixo em checkout limpo, sem depender de `.env` local, PostgreSQL ou artefatos gerados anteriormente:
